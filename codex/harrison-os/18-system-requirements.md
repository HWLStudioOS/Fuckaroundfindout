# Harrison OS System Requirements

Date started: 2026-05-11.

## Core Requirement

The system must be proactive.

Harrison OS fails if Harrison has to:

- Open Codex manually every day.
- Prompt every check-in.
- Keep a Mac Mini running as the only way for the system to work.
- Close sessions to make sure memory is logged.
- Manually carry context between tools.

The system should show up in Harrison's life.

## Failure Modes

Harrison will stop using the system if:

- It feels manual.
- It requires daily prompting.
- It becomes another place to maintain.
- It produces generic summaries.
- It does not send useful messages/emails/notifications.
- It does not capture memory automatically enough.
- It creates complexity before solving daily usefulness.

2026-05-17 real-world test:

- Harrison's Mac Mini was off for a few days while he was in Copenhagen.
- This confirms that a local-only OS cannot be the long-term proactive layer.
- Local Markdown can remain the durable source of truth, but reminders and briefs eventually need a cloud, phone, Telegram, email, or other always-on delivery path.

## What Makes It Feel Alive

The system feels alive when:

- Harrison receives a message/email/notification that is genuinely useful.
- It knows his current goals and constraints.
- It can remind him before things break.
- It can research and synthesize without being asked every time.
- It helps him learn again.
- It turns data into next actions.

## Preferred Home

Likely hybrid:

- Markdown files as durable source of truth.
- Lightweight local/web app as interface.
- Possible Linear layer for projects/tasks.
- Possible email/Telegram/notification layer for proactive pushes.
- Eventually phone app, with TestFlight acceptable for private use.

## Daily Check-In

Harrison would do a 15-minute daily check-in if needed.

Purpose:

- Extract the core truth of the day.
- Capture scores across life areas.
- Turn the day into memory and next actions.
- Keep the recurring operating frame visible: closed loops, calmer cash, delegated editing, and training restraint.

Potential daily questions:

- What is true today?
- What loop needs to close today?
- What cash truth matters today?
- What can be delegated instead of carried?
- Where should you show restraint rather than prove yourself?
- Sleep score / sleep time?
- Body/readiness/training state?
- Mood/energy?
- What is the one thing that matters most today?
- What client obligation needs attention?
- What money/admin issue needs attention?
- What will you learn today?
- What will you do for Maya/relationship/life?
- Where might you avoid reality today?
- What does "enough" look like today?

## Weekly Review

Harrison would do a 45-minute weekly review.

Output:

- Actions for the next week.

Review areas:

- Money.
- Health/training.
- Client work.
- Content.
- Relationship/life.
- Learning.
- Calendar.
- Attention.

Output should include:

- Top wins.
- Reality check.
- Risks.
- Late/at-risk obligations.
- Next week's top three outcomes.
- Client next actions.
- Money next actions.
- Training focus.
- Content commitment.
- Learning brief.
- One grounding reminder.

## Default Tracking

Harrison wants Codex to track:

- Fitness and training routine.
- Sleep and recovery where data is available.
- Learnings and new-to-Harrison information.
- New developments in AI, tech, science, fitness, entrepreneurship, culture, fashion, and sport.
- Client work status.
- Money and receivables.
- Calendar and deep work blocks.
- Content pipeline.
- Relationship/life check-ins.

Harrison says there is nothing Codex should never track unless explicitly asked. Working safety rule: still treat health, finances, relationship, and private communications as sensitive; summarize and act only with care.

## First Useful Version

Harrison's requested first useful version:

- Daily email/message/app notification.
- Sleep and health breakdown similar to Bevel Health or Whoop.
- Training prompt for the day.
- Deep work block mapped out.
- Meal plan: what to eat/cook and when.
- Full day schedule.
- Learning block.
- Piece of wisdom.
- Soft reminder to love himself.

Reality check:

- This is not small.
- The smallest shippable version should start with manual/available inputs and progressively connect real data sources.

## End-Of-June "Holy Shit" Version

Target:

- A phone app.
- Private App Store/TestFlight acceptable.
- Proactive notifications.
- Daily plan.
- Check-in capture.
- Weekly review.
- Learning brief.
- Command Center view.

## Product Principles

- Proactive over passive.
- Useful over complete.
- One trusted intake before many dashboards.
- Memory must update automatically from check-ins.
- Final approval stays with Harrison for money, client comms, public posts, legal/tax, and relationship communications.
- The OS should challenge Harrison without becoming another self-punishment machine.
